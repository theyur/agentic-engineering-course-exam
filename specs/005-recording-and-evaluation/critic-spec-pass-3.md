## Notes

### MINOR-1: HP-009 and ADR 0018 understate what a failed scheduled refresh does to the hosted demo
- **Where**: spec.md HP-009 (l. 627-628: "One late or failed scheduled run only adds a day of Missed at the top of each daily goal's history"); ADR 0018 Consequences (l. 88-89: same sentence).
- **Against**: `.github/workflows/deploy-demo.yml` l. 253-264 (5.2 deletes the database), l. 292-295 (8.1 stops the app), l. 297-333 (9.1 creates the database, 10.1 migrates, 11.1 starts the app); specs/003-demo-hosting/spec.md HP-017 (l. 333-336: "A failed deployment or refresh MAY leave the hosted demo unavailable or incomplete until the next successful one"); the workflow's own failure history (l. 197-199, l. 222-225: failures at 4.2 and 4.5 on 2026-10-25 and 2026-11-15); spec.md SC-005 (l. 719-720).
- **Continues**: new
- **Reasoning**: The sentence holds only when a run fails before step 5.2, or is late. A scheduled refresh that fails at 9.1, 10.1 or 11.1 has already deleted the database and stopped the app. Until the next successful run, the hosted demo is down or empty, with no `demo4` and no seed catalog (slice 3 HP-017). The run is unattended, so the next successful run may be the next day's schedule. Even a run that fails before 5.2 adds no Missed row on the day it fails. On day R + 1 with data from day R, R and R − 1 are still Pending, so a Missed row appears only after two or more days without a successful run. The spec and the ADR therefore give a failure consequence that is too mild. They also set it against SC-005's "on any day until 2027-01-31", which a scheduled failure in the later steps breaks for up to a day.

Run … selftest.ps1": the workflow file is outside that folder); specs/003-demo-hosting/spec.md HP-015 (l. 327-330: the repository MUST document how to refresh the demo); `docs/operations/hosted-demo.md` l. 100-110 (mode table and "After `deploy` and `refresh` …", both describing Operator-started runs only), l. 167-176 (weekly checks) and l. 229 ("Teardown after 2027-01-31", which runs only `teardown.ps1`); `tools/hosting/teardown.ps1` l. 1-3, l. 63-70 (Azure resources, app registration and the GitHub environment, not the workflow file).
- **Continues**: MINOR-1 and MINOR-2 of pass 2, in part
- **Reasoning**: No workflow self-test exists. `selftest.ps1` is the offline provisioning test, so "covers it" means a new kind of check in a script that today never reads the workflow. The spec states this as though it were an existing test. The Operator guide is the document slice 3 HP-015 requires for refreshes. "The teardown steps" are the guide's teardown section plus `teardown.ps1`. Neither can remove a trigger from a workflow file committed on `master`, and the spec does not say where the removal is done or by whom.

### MINOR-3: HP-009 makes "no default time zone" a hosted-demo rule against ADR 0016, which ADR 0018 does not amend
- **Where**: spec.md HP-009 (l. 625-626: "the hosted demo configures no default time zone, so R is the UTC date"); ADR 0018 status line (l. 4-6: amends ADR 0007 and ADR 0015, keeps ADR 0013) and "Run date" (l. 73-75).
- **Against**: docs/adr/0016-time-zones.md l. 79 ("The hosted demo's operator sets the default time zone in the App Service settings (ADR 0015)") and l. 45 (the default is an operator setting); slice 4 FR-025; constitution Decision Discipline ("Changing a recorded decision requires a new or superseding ADR").
- **Continues**: MINOR-6 of pass 2
- **Reasoning**: The fact the author checked is true: `provision.ps1` sets no default. But HP-009 now forbids a default as a MUST, while ADR 0016's consequence has the hosted operator set one. ADR 0018 lists the ADRs it amends, and ADR 0016 is not among them. So the two accepted ADRs disagree on the hosted configuration, and nothing points from 0016 to 0018. The rule is needed only to line the "shortly after midnight UTC" schedule up with `demo4`'s day. FR-030 already defines R in the same time zone as `demo4`, so the data is consistent whatever the default is. The record does not show this either.

### MINOR-4: ADR 0018's new Context gives the wrong day on which rows leave the first History page
- **Where**: docs/adr/0018-evaluation-on-read-and-demo-history.md Context (l. 18-19: "Three days later the 'Reading' goal's Failed day has left the first 10 History rows, seven days later its last Met has too").
- **Against**: spec.md HP-001 (l. 578-579: History lists the commitments that have begun, newest first, the first 10) and FR-030 Reading data (l. 548-551: Failed on R − 6, 25 minutes on R − 2, which is Met once final from R + 1).
- **Continues**: new (detail of the MAJOR-1 resolution)
- **Reasoning**: On day R + 3 the begun rows, newest first, are R + 3, R + 2, R + 1, R, R − 1, R − 2, R − 3, R − 4, R − 5 and R − 6. The Failed day is the 10th row and still on the first page. It leaves on R + 4. The newest Met, R − 2, is the 10th row on R + 7 and leaves on R + 8. The owner-facing question says "after about a week", which still holds. But this is the ADR text that records why manual refreshes were rejected, and each of its counts is one day early. The smoke check's need for "Failed" on the Reading page (HP-008) actually breaks from R + 4 without a refresh.
