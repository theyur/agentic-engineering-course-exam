# Hosted demo: Operator guide

The hosted demo is the one public instance of Habit Tracker on Azure that reviewers use until 2027-01-31. This
page is for the Operator: the person who provisions it, starts deployments, refreshes and checks, holds the
secret configuration and reads the operator log (HP-015).

Decisions: [ADR 0015](../adr/0015-demo-hosting.md). Behaviour and requirements:
[specs/003-demo-hosting](../../specs/003-demo-hosting/spec.md). The workflow's step numbers come from
[contracts/deploy-workflow.md](../../specs/003-demo-hosting/contracts/deploy-workflow.md); where each value
lives is in [contracts/hosted-configuration.md](../../specs/003-demo-hosting/contracts/hosted-configuration.md).

This page states no secret value and no administrator email. Keep it that way.

## What runs where

- One resource group with an App Service plan (Linux, Basic B1), one web app on .NET 10 (HTTPS only, TLS 1.2,
  Always On, one instance), one Azure SQL server with SQL authentication and one Basic database.
- The secret configuration lives only in the web app: the connection string `HabitTracker` and the app settings
  `Operator__AdministratorEmail`, `Operator__AdministratorPassword` and `Operator__DemoPassword`. The SQL
  administrator password exists only inside that connection string.
- GitHub holds no secret. The environment `demo` has non-secret variables only; the workflow reads the secret
  values from the web app at run time and masks them.
- `Deployment__Commit`, an app setting, holds the full SHA of the deployed commit.
- The workflow **Deploy demo** also refreshes the demo every day at 00:20 UTC until 2027-01-31
  ([ADR 0018](../adr/0018-evaluation-on-read-and-demo-history.md); see "The daily refresh").

## Provision

Prerequisites: PowerShell 7; the Azure CLI signed in (`az login`) with rights to create resources and an Entra
application; the GitHub CLI signed in (`gh auth login`) with admin rights on the repository. Provisioning needs
no merge: it can run from any branch that has `tools/hosting/`.

```powershell
pwsh -NoProfile -File tools/hosting/provision.ps1 -Subscription <id or name> -Location <region> `
    -ResourceGroup <rg> -PlanName <plan> -WebAppName <app> -SqlServerName <server> `
    -SqlDatabaseName <db> -Repository <owner/name>
```

None of the parameters is secret. The web app name gives the published address
`https://<app>.azurewebsites.net`.

The script asks for three values, each with a masked prompt and each twice (the second entry must match):

- **Administrator email**: refused unless it is an address at `example.com` (HP-014).
- **Administrator password** and **demo password**: at least 8 characters, with a number (the app's password
  rule). A demo password that breaks the rule makes demo loading fail, and the smoke check with it.

On a later run, Enter keeps the stored value. With no stored value, an empty answer is refused.

It runs eight steps and prints their names and non-secret identifiers only:

1. subscription, and a check that App Service on Linux offers `DOTNETCORE:10.0` (it stops otherwise; pick
   another region);
2. resource group, plan, web app;
3. web app configuration, container logging to the file system, log retention set to 30 days and read back;
4. SQL server (administrator login `htsqladmin`) and the connection string `HabitTracker`;
5. the Basic database and the firewall rules `webapp-out-<n>` for the web app's possible outbound addresses;
6. app settings: `DataProtection__KeysDirectory`, `ASPNETCORE_FORWARDEDHEADERS_ENABLED` and the three values
   above;
7. Entra application `<app>-github-deploy`, its service principal, the federated credential
   `github-environment-demo` and the role Contributor on the resource group;
8. GitHub environment `demo` and its variables.

It ends with the published address. Each step is idempotent, so run the script again after any change: it
creates what is missing and sets every setting again.

### Recovery: a first run stopped after creating the SQL server

The SQL administrator password is generated by the script and written into the connection string at once. If
a run stopped between the two, the next run stops with "the SQL password is unknown: run again with
-RotateSqlPassword". Do exactly that: add `-RotateSqlPassword` to the same command. It sets a new SQL password
and writes the connection string. The same applies when the script reports that writing the connection string
failed.

## Rotate a secret

- **SQL password**: run the provisioning command with `-RotateSqlPassword`, then start a `refresh` run.
- **Administrator email or a password**: run the provisioning command, enter the new value at its prompt and
  press Enter at the others, then start a `refresh` run.

A changed app setting restarts the web app. The refresh gives it a new, empty database with the new values.

## The GitHub environment `demo`

Created by step 8 of provisioning; change it by running the script again, not by hand.

- Deployment branch policy: only `master`. A job on another branch gets no Azure token.
- Variables: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_RESOURCE_GROUP`,
  `AZURE_WEBAPP_NAME`, `AZURE_SQL_SERVER`, `AZURE_SQL_DATABASE`, `DEMO_BASE_URL`.
- No secrets. Never add one: the workflow does not need it.

The workflow signs in to Azure with OpenID Connect through the federated credential, whose subject is the
repository's OIDC subject prefix followed by `:environment:demo`. The prefix is `repo:<owner>/<name>` by default and
`repo:<owner>@<owner id>/<name>@<repo id>` when the repository uses immutable subject claims, as this one does;
`provision.ps1` reads it from GitHub (`gh api repos/<owner>/<name>/actions/oidc/customization/sub`). A sign-in
error `AADSTS700213` in step 1.2 means the two differ: run `provision.ps1` again.

## Run the workflow

GitHub → Actions → **Deploy demo** → **Run workflow**, with "Use workflow from" set to `master`. The workflow can
run only after the PR that adds `.github/workflows/deploy-demo.yml` is merged. A merge or push never starts it;
only you or its daily schedule do (see "The daily refresh").

| `mode` | What it does | `commit` |
|---|---|---|
| `deploy` | Deletes the database, deploys the commit, creates the database again, applies the commit's migrations, starts the app, runs the smoke check | a full or short SHA on `master`, or `master` (default) |
| `refresh` | The same for the deployed commit (`Deployment__Commit`), without deploying | ignored |
| `check` | Changes nothing; runs only the smoke check against the deployed commit | ignored |

- `deploy` takes about 10 minutes, at most 15. The hosted demo is unavailable meanwhile.
- After `deploy` and `refresh`, every registered account and every reviewer change is gone; the startup tasks
  create the administrator, the demo accounts with their custom habits and the seed catalog again, and
  `demo4@example.com` with its results and notes relative to the start's UTC date (slice 5), and
  `demo5@example.com` with 12 weeks of results and notes relative to the same date (slice 6, demo report loading,
  ADR 0021), and `demo6@example.com` with 4 weeks of results, Excused commitments, a past pause and a current
  pause relative to the same date (slice 7, demo pause loading, ADR 0023).
- A second run waits until the first one ends.
- A failed run is recovered by the next run: start it again once the cause is fixed. After a failure at
  `7.1 Deploy the web app`, `Deployment__Commit` is empty and only a `deploy` run repairs it; `refresh` and
  `check` fail at `2.2` with "no deployed commit; run deploy".
- Every run starts with the job **Gate** (step `0.1 Check the trigger and the demo end date`). It has no
  environment and no Azure sign-in; it only sets the mode. The deployment job is then named
  `Demo (<mode>)`.

### The daily refresh

The workflow also runs `refresh` every day at 00:20 UTC (ADR 0018, slice 5 HP-009), so `demo4@example.com`
shows Met, Failed, Missed, Pending and Due results relative to the current date, and `demo5@example.com` (slice 6
HP-011, ADR 0021) its full trends, streaks of several weeks and a result Missed this week, and
`demo6@example.com` (slice 7 HP-010, ADR 0023) Excused results and a goal paused from the day before the refresh
to 5 days after it. Its run is named `Demo (refresh)` and needs nothing from you.

- **After 2027-01-31** a scheduled run ends in **Gate** with the summary "Demo refresh: skipped after
  2027-01-31" and succeeds with `Demo (refresh)` skipped: it never enters the environment `demo` and changes
  nothing. A run you start by hand is never skipped.
- **A late run.** GitHub may start a scheduled run late, or drop it under load. Until it runs, the demo keeps
  the data of the last refresh: every day since then adds an unrecorded day at the top of each daily goal's
  History, Pending first and then Missed. demo4's Failed row of "Reading" leaves the first 10 History rows
  after about 4 days, and the smoke check of a `check` run then fails `demo history demo4@example.com`. demo6's
  current pause ends 5 days after the refresh; from the 6th day "Drinking water" leaves the Paused tab, and
  `demo pause demo6@example.com` fails as well.
- **A failed run** leaves the hosted demo as the step it failed at says ("Read the result"); a failure before
  `5.2 Delete the database` leaves the previous day's data. The next day's run, or a run by hand, recovers it.
- **A refresh by hand.** Run the workflow with `mode` `refresh` (see the table above). Do this after a failed
  or missing scheduled run, or when the demo must be current now. It waits for a running scheduled refresh.
- **Check the schedule when you review the demo.** On the workflow's page in the Actions tab, filter by event
  `schedule`: the last scheduled run should be from today or yesterday.
- **GitHub's 60-day rule.** GitHub turns off the scheduled workflows of a public repository after 60 days with
  no repository activity. For the schedule to last until 2027-01-31, the repository needs activity on or after
  2026-12-02. A turned off workflow comes back only by hand: **Enable workflow** on its page in the Actions tab,
  or `gh workflow enable deploy-demo.yml`. A push alone does not turn it on again. Until then, a refresh by hand
  keeps the demo current.

## Read the result

The run's summary page shows:

| Row | Meaning |
|---|---|
| Mode | `deploy`, `refresh` or `check` |
| Commit | the full SHA that runs (or was meant to run) |
| Result | `succeeded` or `failed` |
| Failed step | the first failed step, as `<n>.<k> <name>` (`Cancelled at` for a cancelled run) |
| Web app started (step 11, UTC) | the start time of the final start; `n/a` in `check` and when the run stopped before |

The step names in the run log carry the same numbers. Typical failures:

- `1.1 Check the ref is master`: the run was started from another branch.
- `2.2 Resolve the commit`: the commit is not on `master`, or nothing is deployed yet (run `deploy`).
- `3.1 Read and mask the hosted settings`: `configuration incomplete: <key>`. Run provisioning to set it. Nothing
  was changed on the hosted demo.
- `10.1 Apply the migrations`: the bundle failed after 3 retries 60 seconds apart. The web app stays stopped.
- `12.1 Run the smoke check`: the app runs, but something is missing. Its lines in the run log say what.

The smoke check writes one line per check, then a timing line and the result:

```text
PASS home
PASS https-redirect
PASS catalog (<found> of <expected>)
PASS administrator
PASS demo demo1@example.com (<found> of <expected>)
PASS demo demo2@example.com (<found> of <expected>)
PASS demo demo3@example.com (<found> of <expected>)
PASS demo history demo4@example.com (14 of 14)
PASS demo report demo5@example.com (<found> of <expected>)
PASS demo pause demo6@example.com (3 of 3)
TIMING first <ms> ms, later <ms> ms (<n> requests)
RESULT PASS
```

A failing check reads `FAIL <name>: <reason>`. `first <ms> ms (retried)` means the first request did not get
the visitor Home; `later n/a` means no demo account signed in. Exit code 1 means a check failed, 2 a broken
invocation. The lines never contain a password, the administrator email or a habit name.

`demo history demo4@example.com` (slice 5) checks demo4's 3 goal names on Goals and 8 texts in the History cards
of two of its goals; since slice 6 also the stat labels "Consistency" and "Streak, commitments" on the page of
"Reading" and the tile label "Due now" on the Home: 14 texts. Its reasons name a goal page only by its number
(1 "Reading", 3 "Yoga"), never by a name, a note, an amount or a path
(`specs/003-demo-hosting/contracts/smoke-check.md`). After a late or missing daily refresh it is the first check
to fail (see "The daily refresh").

`demo report demo5@example.com` (slice 6, check 7) checks demo5's 3 goal names on Goals, the stat label "Streak,
weeks" on the page of "Strength training", and on the Home the tile label "Missed this week" and a "Missed" status
chip: 6 texts. Its reasons name the goal page only by its number (2), and never print a name, a note, a figure or
a path. It needs demo report loading's account, so it fails when that startup task failed or had no valid demo
password (see "Read the operator log").

`demo pause demo6@example.com` (slice 7, check 8) checks "Excused" among the status chips on the page of
"Meditation, 10 min daily", reached through its link on Goals, and, on the Goals page's Paused tab
(`/goals?tab=paused`), the goal name "Drinking water, 8 glasses a day" with a meta text that starts "Paused until"
in the same goal item: 3 texts. Its reasons name the goal page only by its number (1), and never print a name, a
reason, a note, a figure, a date or a path. It needs demo pause loading's account, so it fails when that startup
task failed or had no valid demo password.

## Read the operator log

The operator log is the web app's console output: administrator creation, demo loading, demo history loading
(`Demo history loading: …`, `Demo account demo4@example.com: …`, `Demo goals …`, `Demo records …`), then, as the
fourth startup task (slice 6 HP-011, ADR 0021), demo report loading (`Demo report loading: …` with no or a weak demo
password; otherwise `Demo account demo5@example.com: …`, `Demo goals demo5@example.com: …`,
`Demo records demo5@example.com: …`; `Demo report loading failed; the app starts without it` for a fault), then, as
the fifth startup task (slice 7 HP-010, ADR 0023), demo pause loading (`Demo pause loading: …` with no or a weak
demo password; otherwise `Demo account demo6@example.com: …`, `Demo goals demo6@example.com: …`,
`Demo records demo6@example.com: …`; `Demo pause loading failed; the app starts without it` for a fault) and faults. It
needs an Azure sign-in, and it contains the administrator email, so never paste it into a public place.

- Live: `az webapp log tail --name <app> --resource-group <rg>`, or the portal's Log stream.
- Stored, 30 days: the web app's Kudu site `https://<app>.scm.azurewebsites.net`, folder `LogFiles` (or its
  `api/logs/docker` endpoint). `az webapp log download` may not work on Linux; use Kudu.

Read it against the summary's start time. After it come the results of the final start. In a `deploy` run, the
entries just before it come from the two starts without a database (steps 6 and 7); their
"… failed; the app starts without it" lines are expected and harmless.

## Exam-day and weekly checks

Run `check` on the exam day, 2026-12-14, and at least once a week until 2027-01-31, each time after the app has had no
requests for at least 30 minutes. Add runs until there are at least 10 such idle `check` runs. The workflow's
run history is the record; nothing is committed.

- **SC-006**: every one of these runs succeeds.
- **SC-001**: count only idle `check` runs. Leave out `deploy` and `refresh` runs (they measure a cold start)
  and any `first … (retried)` value. In at least 9 of 10 counted runs, `first` is at most 30,000 ms and
  `later` at most 3,000 ms.
- At the first weekly check, also confirm in Kudu that the first deployment's operator log lines are still
  there (research R-09). If they are gone, the log retention needs another mechanism; report it.

## Monthly cost

At each weekly check, open Cost Management for the resource group and compare the month-to-date cost with
USD 25 (SC-007). The expected cost is about USD 18 a month. There is no budget alert.

## Secret search (SC-004)

With the values shown in the portal (web app → Environment variables: app settings and connection strings),
search, with a tool that keeps no shared log of what you type:

- the repository, including `.github/workflows/deploy-demo.yml` and `tools/hosting/`;
- the downloaded logs of the workflow runs (run page → … → Download log archive);
- the downloaded operator log.

Expected: no password and no connection string anywhere; the administrator email only in the operator log. On
a hit, rotate the value (see "Rotate a secret") and refresh.

## What the exam submission gives reviewers

The exam submission is written outside the repository. It gives reviewers:

| Item | Value |
|---|---|
| Published address | `https://<app>.azurewebsites.net`, the `DEMO_BASE_URL` variable of the environment `demo` |
| Demo emails | `demo1@example.com`, `demo2@example.com`, `demo3@example.com`; with history `demo4@example.com` (slice 5) and `demo5@example.com` (slice 6, the reports with full trends); with excusals and pauses `demo6@example.com` (slice 7) |
| Demo password | the value of `Operator__DemoPassword`; not written here |
| Administrator email | the value of `Operator__AdministratorEmail`; not written here |
| Administrator password | the value of `Operator__AdministratorPassword`; not written here |

The demo password is the same for every demo account. Accounts that reviewers register, and their
changes, last until the next `deploy` or `refresh`. The administrator has no access to private data.

## Run the smoke check locally

The workflow's `check` mode is the usual way. Against a local run (`dotnet run --project src/HT.Ui
--launch-profile https`), set `HT_SMOKE_DEMO_PASSWORD`, `HT_SMOKE_ADMIN_EMAIL` and `HT_SMOKE_ADMIN_PASSWORD`
from your User Secrets by your own means, then:

```bash
dotnet run --project tools/HT.SmokeCheck -- https://localhost:7194 --skip-http-redirect
```

`--warm-up-seconds <n>` sets how long check 1 retries (default 300). The tool takes no secret as an argument.

## Change the scripts

After a change under `tools/hosting/`, run `pwsh -NoProfile -File tools/hosting/selftest.ps1`. It must print
`PASSED`. It runs offline and calls neither Azure nor GitHub.

## Teardown after 2027-01-31

First remove the daily refresh: delete the `schedule:` trigger (its `cron: '20 0 * * *'` entry) from
`.github/workflows/deploy-demo.yml` through a PR to `master`, or at least turn the workflow off with **Disable
workflow** on its page in the Actions tab (`gh workflow disable deploy-demo.yml`). Scheduled runs after
2027-01-31 already end in **Gate** without touching Azure, but they would keep appearing in the run history,
and after the teardown nothing is left to refresh.

Then delete the Azure resources:

```powershell
pwsh -NoProfile -File tools/hosting/teardown.ps1 -Subscription <id or name> -ResourceGroup <rg> `
    -Repository <owner/name> -ClientId <AZURE_CLIENT_ID of the environment demo>
```

It asks you to type the resource group name, then deletes the resource group (web app, SQL server and
database), the Entra application with its service principal, and the GitHub environment `demo` with its
variables. A part that is already gone is skipped, so a second run finishes after a failure.
